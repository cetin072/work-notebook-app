# Existing Web App Reuse Audit

기준 저장소: `cetin072/worklog-voice-pwa`

목적은 상용 Android 앱을 처음부터 다시 설계하지 않고, 현재 실제 사용 중인 웹앱에서 이미 검증된 UX·업무 규칙·데이터 계약·테스트 자산을 최대한 계승하는 것이다.

## 결론

새 Android 앱은 **기존 웹앱의 사용 경험과 검증된 규칙을 계승하되, 로컬 저장·위젯·카메라·오프라인 영역은 Android 네이티브로 새로 구현한다.**

`worklog-voice-pwa`의 Production 코드를 상용 앱 저장소로 통째로 복제하거나 WebView로 감싸는 것은 기본 방향으로 삼지 않는다. 기존 웹앱은 계속 실사용 안정판이자 동작 기준(reference implementation)으로 유지한다.

---

## 1. 그대로 계승할 제품 경험

### A. 기록 흐름
- 앱을 열면 바로 기록할 수 있어야 한다.
- 큰 `말하기` 동작이 중심이다.
- 사용자가 말하기를 중지하면 마지막 인식 결과까지 반영한 뒤 저장한다.
- 저장 성공 여부를 즉시 명확히 보여준다.
- 직접 입력도 항상 가능해야 한다.

### B. 초안 보호
현재 웹앱은 작성 중 텍스트와 입력값을 임시 보관하고 재실행 시 복구한다.

Android에서는 localStorage 대신 Room/로컬 draft 상태로 구현하되, **앱이 중단되거나 화면을 나가도 작성 중 기록을 잃지 않는다**는 동작을 계승한다.

### C. 사용자 입력 우선
기관/상태/유형 등을 자동 추론하더라도 사용자가 직접 바꾼 값은 자동 추론이 다시 덮어쓰지 않는 현재 원칙을 계승한다.

상용 앱 초기 Local MVP에서는 자동 추론을 최소화하지만, 향후 규칙/AI가 추가되어도 이 원칙은 유지한다.

### D. 여러 업무 분리 개념
현재 웹앱은 `다음 업무`, `다음 건`, `그다음` 등으로 여러 건을 구분해 저장한다.

초기 Android Local MVP의 필수 범위는 아니지만, 음성 입력 단계에서 재도입할 때 기존 분리 규칙을 기준으로 포팅한다.

### E. 브리핑 경험
현재 웹앱의 핵심 가치는 단순 저장이 아니라 `기록 → 축적 → 오늘 다시 보여줌`의 루프다.

Android에서도 장기적으로 다음 표시 모델을 계승한다.
- 오늘 우선 업무
- 오늘 일정
- 다가오는 일정
- 확인 필요
- 완료 처리 및 취소
- 오래된 브리핑/데이터에 대한 경고

초기 Local MVP에서는 AI 브리핑 대신 로컬 날짜/완료상태 기반의 단순 `오늘 할 일`로 시작한다.

## 2. 코드/로직별 판정

| 기존 자산 | 판정 | Android 처리 |
|---|---|---|
| `public/app.js` 음성 세션/결과 병합 | **이식** | JavaScript를 그대로 쓰지 않고 Kotlin 동작으로 포팅 |
| `mergeWithOverlap` 중복 음성 조각 병합 | **이식 우선** | Galaxy 계열 음성인식에서 이미 필요성이 확인된 동작으로 회귀 테스트 작성 |
| 연속 듣기/무음 후 재시작 | **이식 후보** | Android 음성 입력 구현 시 플랫폼 방식에 맞게 재구현 |
| 작성 중 draft 복구 | **계승 필수** | Room 또는 SavedState + 영속 draft로 구현 |
| `public/quick-save.js` 중지→즉시 저장 UX | **계승 필수** | 네이티브 화면 동작으로 재구현 |
| `splitWorkItems` 분리 규칙 | **이식** | 음성 다건 입력 단계에서 Kotlin 규칙/테스트로 포팅 |
| `inferFields` 가벼운 규칙 추론 | **나중 이식** | Local MVP에서는 최소화, Smart 단계에서 재검토 |
| `public/inference-guard.js` 수동 선택 보호 | **개념 계승** | 사용자 변경값 우선 정책으로 구현 |
| `public/request-id.js` 요청 재시도 중복 방지 | **나중 재사용** | 로컬 저장에는 불필요. 클라우드/Notion sync 도입 시 idempotency 설계로 재사용 |
| `public/briefing.js` TOP/오늘/다가오는 일정 모델 | **제품 모델 계승** | Compose UI + 로컬 Query로 먼저 구현, AI 연결 후 고도화 |
| 브리핑 freshness 경고 | **계승** | 마지막 계산/동기화 시각 표시 정책으로 재사용 |
| 완료 처리/실행 취소 | **계승** | Local MVP부터 완료 토글, 이후 undo UX 적용 |
| `netlify/functions/worklog.mts` 업무 데이터 계약 | **스키마 참고** | Room WorkItem 필드 설계의 출발점으로 사용 |
| Notion 저장 API 코드 | **초기 제외** | 개인 Notion Connector 단계에서 참고 |
| `auth.js`, `setup.js`, 개인 PAT 연결 | **초기 제외** | 상용 기본판은 로그인/Notion 없이 사용 가능해야 함 |
| Kakao OAuth/예약 전송 | **기존 앱 전용 유지** | Android Local MVP로 이식하지 않음 |
| PWA manifest/service worker | **이식 안 함** | Android 앱에는 네이티브 manifest/resources 사용 |
| 기존 아이콘/`업무수첩` 브랜드 | **재사용** | Android adaptive icon 규격으로 옮김 |
| 기존 회귀 테스트/모바일 검수 시나리오 | **재사용 우선** | 플랫폼 중립적인 동작을 Android 테스트/Acceptance 기준으로 변환 |

## 3. 기존 데이터 모델에서 가져올 것

현재 웹앱/Notion 계약에서 다음 개념은 유지 가치가 있다.

- 제목 (`업무명`)
- 내용/원문
- 기록일/생성시각
- 기한
- 상태
- 유형
- 기관/소속
- 담당자
- 후속조치
- 금액
- 원본 음성
- 증빙/첨부

하지만 Local MVP의 기본 WorkItem은 사용 복잡도를 낮추기 위해 다음만 우선 노출한다.

- id
- title
- content
- dueDate
- dueTime
- completed
- createdAt
- updatedAt
- photo references
- voice references

기관/유형/담당자/금액/후속조치는 DB 확장 가능성을 열어두되 첫 화면의 필수 입력으로 강제하지 않는다.

---

## 4. 그대로 복사하지 않는 이유

기존 웹앱은 `Web Speech API → Netlify Function → Notion`을 전제로 한다.

새 앱의 핵심은 반대로:

`Android Native → Room/SQLite → 선택적 외부 Connector`

이다.

따라서 HTML/CSS/JavaScript 전체를 복제하면 단기적으로는 빨라 보여도 다음 기능에서 이중 구조가 된다.

- 홈 화면 위젯
- 완전한 로컬 저장
- 사진/문서 촬영
- 음성/사진 파일 관리
- 오프라인 동작
- Android 권한/백그라운드 처리

그래서 **기존 코드는 reference로 읽고, 검증된 동작과 테스트 계약을 네이티브 코드로 옮기는 것**을 기본 원칙으로 한다.

---

## 5. 첫 구현에 즉시 반영할 재사용 항목

MVP 1에서 처음부터 적용할 것은 다음이다.

1. `업무수첩` 이름과 현재 브랜드 방향
2. 빠른 기록 중심 화면 구조
3. 직접 입력 → 저장 흐름
4. 작성 중 내용 자동 보존/복구
5. 제목/내용/날짜/시간/완료 여부의 WorkItem 구조
6. 완료/미완료 전환
7. 오늘 날짜의 미완료 항목을 `오늘 할 일`로 보여주는 모델
8. 현재 웹앱과 별도 저장소/별도 앱으로 운영하여 실사용 Production에 영향 없음

음성의 `mergeWithOverlap`, 연속 듣기, 다건 분리는 **MVP 1 다음 음성 단계에서 우선 이식**한다.

## 6. 상용화 개발 중 기존 앱 운영 원칙

- `cetin072/worklog-voice-pwa/main`은 현재 실사용 Production으로 계속 유지한다.
- 상용 Android 개발 때문에 기존 Production을 변경하지 않는다.
- 기존 앱의 버그 수정이 필요하면 기존 저장소에서 별도 Issue/PR로만 처리한다.
- 새 앱이 안정되기 전까지 기존 업무수첩을 폐기하거나 데이터 흐름을 강제 이전하지 않는다.
- 새 앱은 일정 기간 병행 사용 후 전환 여부를 결정한다.
